# 立项文档：插件接口 增量3——Wasm 插件宿主（Plan 22 候选）

> 状态：**立项预研，未批准实现**。只做路线比选、接口草案、体积分账与风险；批准后另出实现
> spec/plan。前置事实：增量1（声明式高亮）与增量2（QuickJS 逐行解析）已交付，`features.md`
> 待做第 1 条只剩这一步。

## 1. 要解决的问题

增量2 的解析插件有两个天花板：

1. **逐行模型**：`parseLine(line, ctx)` 处理不了多行记录、块结构、需要跨行状态的二进制/半结构化格式
   （如 PCAP、CAN FD 原始帧流、私有二进制日志）；
2. **JS 性能**：百万行级文件的逐行回调开销大，而这类重解析恰是插件最有价值的场景。

Wasm 插件 = 把解析逻辑编译成 wasm 模块（Rust/C/Go 皆可出），宿主按块喂字节流，插件批量吐记录。

## 2. 路线比选

| 路线 | 运行方式 | 新增体积 | 速度 | 生态/调试 | 主要风险 |
|---|---|---|---|---|---|
| **A. wasmtime**（JIT） | Cranelift 编译执行 | **+15–25MB** | 原生级 90%+ | wit-bindgen 成熟、栈/内存/wasm 场景标杆 | 体积与"轻量"定位直接冲突；MSRV/平台矩阵 |
| **B. wasmi**（解释器） | 纯解释 | +2–3MB | 慢 10–30×，但解析是粗粒度批处理，摊薄后可接受 | 纯 Rust、接口标准 wasm；调试一般 | 无 SIMD 等高级特性；极端热点仍慢 |
| **C. Extism** | wasmtime 之上的插件框架 | +15MB+（含 wasmtime） | 同 A | 多语言 PDK（Rust/C/Go/…）SDK 最省事 | 双重抽象，出问题要穿两层；体积同 A |
| **D. 不引入 wasm，扩展 QuickJS**（给解析插件加块缓冲/多行 ctx API） | 现有 rquickjs 沙箱 | ≈0 | JS 字节处理慢，可借 base64/Uint8Array 缓解 | 无新概念 | 解决多行模型，解决不了性能天花板；"重解析器"诉求只算半满足 |

已排除：独立进程插件（IPC/打包复杂度数倍于收益）、动态库插件（安全模型不可接受）。

## 3. 建议

**选 B（wasmi）起步，预留 A。** 理由：体积代价约 1/10，对"解析器插件"这一场景
（一次喂一块、批量出记录）解释器足够；wit/ABI 设计与运行时无关，未来换 wasmtime 是换执行器
不是换接口。C 的 PDK 生态是增量2 之后才有的甜头，立项时不必为它背 JIT 体积。

## 4. 接口草案（wit 心智稿，实现前再冻结）

```wit
package lumelog:plugin;

interface parser {
  /// 打开时自报：id/name/扩展名/列定义（对应增量2 的元数据）
  metadata: func() -> plugin-info;
  /// 喂一块原始字节（文件顺序）；返回本块内解析出的记录。
  /// 宿主保证按序、可重复调用；插件自带跨块状态（二进制帧边界缓冲）。
  parse: func(chunk: list<u8>, base-line: u64) -> result<list<record>, parse-error>;
  /// 流结束：冲刷插件内部缓冲（尾帧）。
  finish: func() -> list<record>;
}
```

- 记录 `{ line: u64, cells: list<string> }` 沿用增量2 的 `ParserRow`，**前端表格/导出零改动**；
- 沙箱边界：无 fs/net/时钟/随机源；fuel 或 epoch 限速 + 内存上限（沿用脚本引擎 64MiB 档位）
  + 总超时 + 可取消；
- 插件位置与清单沿用 `plugins/` 目录（`*.wasm`），元数据仍从 `metadata()` 读，列表页不执行解析逻辑。

## 5. 体积分账与风险

- wasmi 及其依赖估 +2–3MB（安装包 15MB 上限内，需在 CI 体积门槛里挂账核对，P6 ≤15MB）；
- 风险：ABI 一旦发布即兼容负担（先 `unstable` 标注、单版本窗口）；畸形 wasm 的 panic 面
  （wasmi 返回 Result，宿主兜底）；插件作者需要 Rust 工具链（文档给 cargo 模板）。

## 6. 工作量与验收轮廓

约 2 个 plan：宿主（wasmi + fuel/内存/取消 + wit 生命周期）为一个；流式管线（块喂入、
`finish` 冲刷、复用 ParserPanel）+ Rust/Go 双示例插件模板 + 文档为一个。
验收轮廓：现造 wasm fixture（宿主测试直接实例化模块）、端到端解析二进制格式、取消/超时、
体积门槛核对、示例插件走通"cargo build → 丢进 plugins → 表格出数"。

## 7. 决策点（批准时需拍板）

1. 是否接受 B（wasmi）而非 D（QuickJS 扩展）——若当前无真实的二进制格式插件需求，D 或"继续推迟"
   都是合理选项；
2. wit 接口冻结时机（建议实现 spec 评审时）；
3. 安装包体积上限是否为 15MB 硬门槛（是则本项必须过 P6 复测）。
